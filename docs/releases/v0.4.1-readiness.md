## Acceptance limits

- Ubuntu 24.04 native acceptance covered APT install, upgrade from v0.4.0, removal and purge, service and D-Bus integration, CLI diagnostics, isolated-session and missing-provider behavior, a safe PolicyKit denial, and headless GTK startup under Xvfb. Interactive GUI use and authorization prompts were not tested.
- Ubuntu 26.10: logs record a fresh local-DEB installation of `rog-helper 0.4.1`; installed binary hashes matched the staged DEB and read-only telemetry was observed. Upgrade, removal/purge, and interactive PolicyKit behavior were not tested there.
- Ubuntu 26.04 and Debian 13 have dependency-resolution evidence only. The tested DEB is incompatible with Debian 12. The minimum supported runtime distribution remains unestablished.
- Physical fan, Aura, battery, CPU, and GPU control behavior is not claimed as validated. Unverified hardware writes remain gated.

## Security status

- The refreshed audit reported no vulnerability. Four unmaintained-dependency warnings remain: `zbus_names 4.3.1` (RUSTSEC-2026-0371), `zvariant 5.9.2` (RUSTSEC-2026-0370), `zvariant_derive 5.9.2` (RUSTSEC-2026-0372), and `pin-utils 0.1.0` (RUSTSEC-2026-0441). These are maintenance notices, not confirmed exploitable vulnerabilities; the refreshed audit found no lockfile vulnerability advisory. Preserve these warnings; do not suppress them.
- Unsigned executable replacement remains disabled. Automatic battery hardware writes remain disabled. Fan control remains fail-closed unless exact hardware capability and safety validation pass; generic PWM and uncertain channels stay read-only.
- No privileged helper, PolicyKit, D-Bus, or udev permission boundary was loosened by the release changes.

## Publication boundary

The solo-maintainer policy allows Actions to create a draft without deployment approval. The release run requires successful build, tests, Clippy and RustSec checks, validates DEB and RPM metadata, and verifies the exact nine-file inventory and both checksum manifests. It records the tag, commit, workflow run and file hashes. Before the draft job runs, the preflight checks that the live tag resolves to the verified commit at the tip of `main` and checks the saved environment settings. Only the draft job has release write access.

### Administrator environment setup

Before tagging, open **Settings → Environments → release-publish** in the repository. Keep the existing environment.

1. Under **Deployment protection rules**, turn off **Required reviewers**, removing any saved reviewers. **Prevent self-review** does not apply once required reviewers are off. Disable the wait timer and any custom deployment protection rules.
2. Clear **Allow administrators to bypass configured protection rules** and save the protection settings.
3. Under **Deployment branches and tags**, choose **Selected branches and tags**. Remove every existing rule other than the exact **Tag** rule `v0.4.1`; add it if missing. Do not add a branch rule or a wildcard. Save and reload to confirm the settings persisted.

For future releases, replace the old tag rule with the exact tag for the new Cargo workspace version and provide matching release notes. The workflow derives versioned filenames from the validated version.

## Readiness decision

After this change is merged, wait for CI on the intended `main` tip to pass, confirm the saved environment, and tag that exact commit when ready. Keep `main` at that commit until release preflight passes. The maintainer must inspect the successful release run, draft notes, nine assets and checksums before manually selecting **Publish release**. If the run fails or leaves an incomplete draft, do not publish it. The documented distribution, authorization and hardware limits still apply.

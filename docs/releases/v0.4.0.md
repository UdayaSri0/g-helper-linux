# rog-helper v0.4.0

This significant feature update builds on v0.3.1 with persistent named presets, opt-in AC/battery
automation, a graphical eight-point fan-curve workflow, manual X11 refresh-rate control,
desktop-bindable semantic commands, safer Aura validation, stronger fan recovery, and more useful
support diagnostics. Existing capabilities remain hardware- and backend-dependent.

[Compare v0.3.1...v0.4.0](https://github.com/UdayaSri0/g-helper-linux/compare/v0.3.1...v0.4.0)

## Highlights

- A graphical eight-point curve editor and stronger transaction/recovery safety for the narrowly
  verified ASUS WMI fan contract.
- Refined Lighting UI outcomes plus a supervised, exact-target Aura validation sequence that keeps
  accepted-without-readback distinct from physically observed behavior.
- A typed, PolicyKit-gated privileged helper for approved CPU, fan, lighting, keyboard-brightness,
  and battery operations while the GTK UI and session daemon remain unprivileged.
- Persistent named hardware presets plus an opt-in daemon AC/battery policy engine with debounce,
  duplicate suppression, manual override, and explicit Resume.
- A default-redacted `rog-helper issue-report`, more precise install health, and truthful platform
  profile readback confirmation.
- Settings, lifecycle, package-integration, and desktop experience improvements throughout the
  GTK4/libadwaita application.
- Manual X11 internal-panel refresh-rate selection and semantic CLI commands suitable for
  desktop-owned custom shortcuts.
- Stronger Debian/RPM/Arch/Flatpak/AppImage metadata, package lifecycle checks, and isolated
  session smoke testing.

## Fan Control

The existing Cooling telemetry experience continues to adapt to the RPM channels Linux exposes,
keeping read-only and uncertain mappings visible. v0.4.0 extends it with per-mapped CPU/GPU/Mid
selection and a graphical curve workflow.

For hardware matching the exact reviewed ASUS WMI eight-point fan-curve ABI, users can import the
current curve, edit exactly eight temperature/duty points, use conservative local presets, reset a
draft, apply after live validation, or restore Auto/BIOS control. Draft editing and dragging never
write hardware. Temperatures must increase strictly, duty may not decrease, high-temperature safety
minimums are enforced, all values are staged before custom mode is enabled, and supported writes
are read back. Partial failure attempts Auto rollback, while the privileged path preserves a
root-owned recovery marker for restart/shutdown recovery.

Generic `pwm*`, RPM-target, boost, and sync candidates remain diagnostic-only. A writable-looking
sysfs file is not treated as proof that a fan operation is safe.

## Lighting & Aura RGB

Lighting UI 2.0 continues to expose only controls reported by the selected backend. v0.4.0 refines
effect-specific control gating and distinguishes readback-confirmed, accepted-without-readback,
authorization-denied/cancelled, and disappeared-backend outcomes. Merely editing a draft never
authenticates or writes hardware.

The new supervised `rog-helper lighting-test --safe-sequence` is dry-run by default, requires an
exact-target confirmation before writing, refuses unsafe readiness states, uses a fixed high-level
sequence, and ends with a neutral Static restore. A human must still record what the LEDs did.

Aura control is intentionally narrow:

- the preferred DBus backend accepts only the exact reviewed asusd 6.3.8–6.4.0 Aura contract;
- the native HID backend is allow-listed only for the G615JMR target identity (board prefix
  `G615JM`, USB `0b05:19b6`, interface `00`, exact descriptor/protocol);
- active ASUS-daemon ownership suppresses native HID to avoid conflicting writers;
- native reports are fixed, bounded, rate-limited, and duplicate-suppressed.

The native target is single-zone RGB with Static, Breathe, Rainbow Cycle, Rainbow Wave, and Pulse.
It does not claim ARGB, multi-zone, or per-key support. Native success means the request was
accepted; the protocol has no reliable physical effect-state readback.

## Performance & CPU

The v0.3.1 CPU telemetry and capability-gated controls remain available, including per-logical-CPU
state, package power where exposed, history graphs, turbo, governor, energy-performance preference,
frequency limits, and online-state controls. This release does not claim a new CPU hardware
backend.

ASUS platform profiles continue through asusd and now require actual readback before the requested
state is shown as confirmed.

## GPU & Display

GPU mode control remains delegated to supergfxd. Potentially disruptive transitions remain a
deliberate manual action and are not silently forced by automation. NVIDIA telemetry is queried
daemon-side at a bounded interval and degrades field-by-field when unavailable.

On X11, Settings can discover the connected internal panel and manually select an advertised
refresh rate for its current resolution. The backend re-discovers before Apply, confirms the
result, and attempts to restore the previous rate on failure. It does not change resolution or
external outputs. Wayland refresh control and AC/battery refresh automation are not implemented.

## Automation & Profiles

The existing versioned XDG configuration now stores semantic named presets with stable IDs.
Presets can be created, duplicated, renamed, edited, and deleted without applying hardware. Saved
fan curves retain semantic CPU/GPU/Mid roles and validated points—not sysfs paths—and saved lighting
uses modes and colours rather than HID packets.

The daemon owns one opt-in AC/battery policy state machine with a five-second transition debounce,
duplicate-write suppression, persistent manual override, and explicit Resume. The current safe
automatic subset applies asusd platform profiles and asusd/direct-writable battery limits. Fan,
lighting, privileged battery, and GPU fields are reported as skipped; risky GPU transitions never
log out, reboot, or terminate a session.

## Setup & Access

The Setup & Access page and `rog-helper setup-check` distinguish installation health, optional
provider availability, hardware capability, direct-write permission, helper compatibility,
PolicyKit availability, and authorization state. Opening diagnostics is read-only and does not
trigger authentication, install packages, alter permissions, or run the UI as root.

## Diagnostics & Issue Reporting

The CLI now includes richer capability, fan, lighting, helper, setup, service, and DBus diagnostics.
`rog-helper privileged-status` checks the helper API and installed systemd, DBus, PolicyKit, udev,
Aura identity, descriptor, and protocol integration without a hardware write.

`rog-helper issue-report > issue-report.md` produces copy-friendly Markdown redacted by default.
It includes allow-listed build/host, readiness, capability, fan/Aura identity, policy-state,
warning-count, display, and shortcut information. It omits hostname, serial numbers, profile names,
configuration, process telemetry, broad DBus discovery content, and freeform provider/policy errors;
home paths and control characters are redacted. Review any report before sharing it.

## Desktop Experience

The desktop application retains its Dashboard, CPU/GPU/Battery/Memory, Lighting, Cooling,
Setup & Access, Diagnostics, and About experiences. v0.4.0 adds named preset and automation controls,
manual display-rate controls, shortcut guidance, and further lifecycle and state-reporting polish.

ROG Helper does not capture global keyboard input. Users may bind semantic daemon-backed commands
for profile cycling, keyboard-brightness changes, and automation pause/resume in their desktop's
shortcut settings. GPU switching is intentionally excluded from one-key actions.

## Privileged Helper & Security

The optional root helper exposes only typed, semantic, path-free methods. Callers cannot submit
filesystem paths, programs, shell commands, environment variables, or raw HID packets. Each write
category has a fixed PolicyKit action, inputs are validated before authorization where possible and
revalidated at write time, supported backends use readback, and fan recovery remains marker-gated
and Auto-only. The hardened systemd service, restricted system-bus policy, and root-only Aura udev
alias remain part of native packages.

## Packaging & CI

- Debian payload validation now checks required integration, modes, unresolved templates, and
  modeled fresh-install/reinstall/upgrade/remove/purge behavior.
- Session smoke tests use isolated DBus namespaces and exercise daemon start/stop, introspection,
  CLI actions, UI startup, and missing-provider degradation without activating host services.
- Release metadata checks cover the desktop file, AppStream, icons, systemd, DBus, PolicyKit, udev,
  Arch metadata, licensing, and expected binaries.
- The release workflow validates and publishes Debian, AppImage, tarball, direct binaries,
  checksums, and a Fedora-built RPM.
- The CI session smoke test now uses portable `grep` assertions and no longer depends on an
  undeclared `ripgrep` installation.

## Upgrade Notes

The v0.4.0 configuration schema migrates older configuration through the existing versioned XDG
store, preserves supported unknown fields, validates fields independently, and writes atomically.
Saving or migrating a preset does not apply hardware.

For Debian, Ubuntu, or Linux Mint, download the release `.deb` and run:

```bash
sha256sum -c rog-helper-0.4.0-SHA256SUMS.txt --ignore-missing
sudo apt install ./rog-helper_0.4.0_amd64.deb
rog-helper privileged-status
```

The package manager refreshes systemd, DBus, PolicyKit, and udev integration. If the desktop still
shows an old session daemon after upgrade, log out and back in or restart the user service. Reboot
is not a general upgrade requirement; a GPU mode may independently require logout or reboot when
supergfxd reports that requirement.

## Known Limitations

- Hardware support is capability-driven and the model-by-model validation matrix is incomplete.
- ASUS WMI fan curves are deliberately limited to the exact verified eight-point topology; generic
  writable PWM/RPM files are not exposed as controls.
- G615JMR native Aura support is narrow and remains physically unvalidated through ROG Helper;
  accepted HID writes are not physical LED confirmation.
- Fan Apply, rollback, recovery-marker restart behavior, and Auto/BIOS restoration still require a
  committed supervised physical validation record.
- The exact asusd Aura adapter supports only the reviewed 6.3.8–6.4.0 contract. Unknown contracts
  remain diagnostic-only. Platform profiles require asusd, and GPU switching requires supergfxd.
- Automation intentionally applies only platform profiles and non-interactive battery-limit paths.
  Saved fan, lighting, privileged battery, display, and GPU fields are retained but skipped.
- Display refresh selection is manual and X11-only. Wayland and AC/battery display rules are not
  implemented; keyboard idle timeout is also not implemented.
- Global shortcuts are owned by the desktop and must be configured by the user; the application
  performs no global key capture or registration.
- AppImage cannot safely install the root helper, system-bus policy, PolicyKit policy, system
  service, or udev rule. Use a native package for the full privileged integration.
- Flatpak has no direct sysfs write access and host services may reject sandboxed callers.
- Release CI provides package-build evidence, not physical hardware validation.

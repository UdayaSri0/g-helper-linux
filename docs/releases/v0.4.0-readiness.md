## Major Changes

- Persistent semantic named presets and opt-in daemon AC/Battery policy with a limited supported
  apply subset, manual override, and explicit Resume.
- Graphical eight-point ASUS WMI curve editing, validation, readback, rollback, and serialized
  marker recovery.
- Manual X11 internal-panel refresh selection and daemon-backed shortcut commands for desktop
  custom bindings.
- Supervised Aura validation workflow and clearer accepted/readback/error outcomes.
- Default-redacted issue reports and more accurate profile confirmation, diagnostics, and package
  integration checks.

See [v0.4.0 release notes](v0.4.0.md) for full details and limitations.

## Hardware Validation

Software/test validation and physical validation are separate. The host smoke and fixture suite
exercise control-flow and degradation behavior but do not write fan or lighting hardware. No new
physical test is claimed for v0.4.0. G615JMR native Aura, ASUS WMI fan Apply/Auto/rollback/recovery,
and model-by-model hardware behavior remain unvalidated; see [HARDWARE_SUPPORT.md](../HARDWARE_SUPPORT.md).

## Known Limitations

- Fan-curve support remains limited to the verified ASUS WMI topology; generic PWM/RPM-target,
  sync, boost, and hysteresis controls remain unsupported.
- Native Aura is restricted to the G615JMR identity and has no effect-state readback; ARGB, zones,
  and per-key lighting are unsupported.
- Automation applies only asusd platform profiles and asusd/direct-writable battery limits.
  Privileged-only battery, GPU, fan, lighting, and display fields are skipped.
- Display refresh selection is manual and X11-only. Wayland, automatic refresh switching, and
  keyboard timeout are unsupported.
- AppImage cannot install the privileged helper/system integration; Flatpak lacks direct sysfs
  writes; optional asusd and supergfxd services remain feature dependencies.
- No complete model-by-model hardware matrix exists.

## Release Workflow

`.github/workflows/release.yml` triggers on `v*` tags, verifies the tag matches the workspace
version, runs Rust validation, builds and validates Debian/tarball assets, builds AppImage, stages
an APT preview, uses `docs/releases/${tag}.md` as the release body, and uploads a Fedora-built RPM
and matching RPM checksum file. The tag must not be created until the final `main` SHA has passing
required CI and all release gates below are resolved.
